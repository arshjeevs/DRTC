Abstract

Large vision-language-action and action-chunking policies often require GPU servers, forcing low-cost robots such as the SO-101 arm to rely on remote inference over wireless links. When network replies are delayed or lost, the client shipped with LeRobot 0.7 ends runs after one second of queue starvation and replaces a lost request only once its queue has run dry. We port Distributed Real-Time Chunking (DRTC) into LeRobot 0.7 with four fixes discovered under slow links and short chunks, implement six smoothing methods and six injectable network fault types, and build a replay bench to evaluate seven policies across two manipulation tasks. In a first robot study on sorting (80 trials), faults reduced shipped-client success to 0% for both SmolVLA and GR00T N1.5, whereas DRTC achieved 60% (SmolVLA) and 80% (GR00T N1.5). Against a patient baseline on the bench across seven policies, DRTC's cooldown re-request drives recovery from drops and outages, though it stalls more under rising latency, and smoothing cuts jerk 3–20×.

The problem

Large robot policies—vision-language-action models of 0.45 to 3.4 billion parameters—need a GPU server and are too big for the laptop or Raspberry Pi that drives a low-cost arm like the SO-101. In remote inference, the robot computer sends camera images and joint positions over the network and plays back chunks of future actions at 30 actions per second so execution can overlap with server inference.

Wireless links suffer latency spikes, dropped replies, and brief outages, which drain the robot's action queue and stall the arm. LeRobot 0.7's shipped client ends a run after one second without actions and replaces a lost request only once its queue has run dry, so a single short fault can end the task. Distributed Real-Time Chunking (DRTC) addresses this with early requests, RTT estimation, and cooldown re-requests, and we evaluate it against LeRobot's own client under controlled faults, take it apart to see which parts matter, and pair it with motion smoothing.

What we built

1 · Client scheduling

DRTC on LeRobot 0.7 with four fixes

Ported DRTC's early trigger, Jacobson–Karels latency estimator, and cooldown re-request inside LeRobot 0.7's runtime with all safety checks, adding four fixes found on slow links and short chunks: removing the half-chunk cooldown cap, flooring the cooldown by recent replies to stop re-request storms, allowing a 10 s initial reply wait, and capping RTC delay.

2 · Testing infrastructure

Network fault injection and a replay bench

Added deterministic, trial-shifted injection of six fault types directly in the client transport, paired with a replay-robot plugin that streams held-out episodes over simulated 250–270 ms WiFi latency so all seven policies run cleanly on one machine.

3 · Motion quality

Six smoothing methods

Implemented a causal Butterworth filter, zero-lag queue smoothing, guided Real-Time Chunking (RTC), temporal ensembling, adaptive playback, and a minimum-jerk resume ramp, tested individually and combined using a pre-registered lag-guarded selection rule.

4 · Reproducible science

Evaluation framework rebuilt from raw records

Built an experiment registry pinning rigs, datasets, recipes, model commits, and frozen plans, running trials in seeded rounds and rebuilding every metric, table, and figure directly from the raw trial records.

Results

First robot run on the sorting task (80 trials) under a mix of a 1 s latency spike, 1 s of lost replies, and a 1.5 s outage, followed by seven-policy replay-bench studies (setup v2):

Condition (first robot run, sorting) SmolVLA GR00T N1.5
Normal network, LeRobot as shipped 90% 70%
Faults, LeRobot as shipped 0% (client ended every run) 0% (client ended every run)
Faults, DRTC 60% 80%
Faults, DRTC + smoothing 80% (4.8× less jerk) 100% (10.8× less jerk)
Honest negatives

Rising latency: When every reply slowed by 0.4 s for 5 s, DRTC stalled more than a patient LeRobot client on every policy because its cooldown tracks recent faster replies and aborts valid slower ones. Slow-link RTC: Guided Real-Time Chunking (RTC) hurt on our network-dominated link—roughly doubling SmolVLA's stalls—because the extra inference time cost more stalls than smoother seams saved.

Reproduce

Every official trial is stored raw in a results store on the Hugging Face Hub, and reports are rebuilt from it:

.venv/bin/lab eval report sort_one_drtc_main --pull     # one evaluation's tables and statistics
make -C report                                          # the report: numbers, tables, figures, PDF
.venv/bin/python presentation/build.py                  # the slides
.venv/bin/python presentation/video.py                  # the project video
