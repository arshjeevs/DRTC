\chapter{Edge Deployment on the Raspberry Pi}\label{ch:edge}

\section{Introduction}

Remote inference matters most where the robot computer is smallest. The last step of the platform was therefore to
run the robot side on a Raspberry Pi~5 instead of the laptop, with the policy still on a GPU server.

\section{Setup}

The Pi~5 (8~GB, Debian, no GPU) runs the same software as the laptop with a CPU build of PyTorch, installed by one
setup script. It uses the same arms and calibration files, copied from the laptop rather than recalibrated, so a
policy sees the same joint values on either computer; the rig file lists the arms' serial ports for each machine. The
Pi connects to the laptop's WiFi hotspot. It can use any of the model servers: the A100 or the H200 through an SSH
tunnel with its own key, or the laptop's GPU directly, in which case the laptop serves on its hotspot address and the
Pi connects without a tunnel. The evaluation framework records the robot computer of every trial, and reports never
average across robot computers.

\section{First test}\label{sec:edge-first}

A test session (not counted) ran the cube-in-box baseline plan from the Pi with the models on the A100. The control loop
held \R{edge/hz} with no dropped video frames, so the Pi has enough capacity for the robot side at 30~Hz. The round trip,
however, roughly doubled compared with the laptop: \R{edge/smolvla/rtt} for \smolvla{} and \R{edge/groot/rtt} for
\groot, because every request now crosses the hotspot's WiFi to the laptop before reaching the server. With the
shipped client, \groot's 16-action chunk (0.53~s) was shorter than its round trip, and the queue ran dry even without
faults.

\section{What it means}

The edge is exactly the situation the redesigned experiments are about: a slower, less reliable link and short chunks.
The two measures that help on the laptop help more here: \drtc's earlier trigger and its re-request, as would compressing
the images, which make up most of each request. The Pi then became the robot computer of the official robot trials: the baselines of all seven policies and the
robot experiment E4.

\section{The Pi as the robot computer for the baselines}
The robot baselines of Section~\ref{sec:baselines} ran from the Pi, with every model served from the H200: 70 counted
trials per task, all seven policies, over the laptop's WiFi hotspot. The Pi kept the control loop at its rate in every
counted trial (median 29.9~Hz, never below 29.1~Hz), so the CPU of the Pi is not a limit for the robot side. The link
is: over WiFi the client measured a reply turnaround of 0.87~s at the median and 1.32~s at the 95th percentile across
all policies, with a worst case of 4.2~s (Figure~\ref{fig:edgertt}), three to four times the 250~ms the bench assumes.

Running from the Pi also brought practical problems, each handled inside the evaluation framework rather than by
editing results. A loose power plug of the follower arm made the motors disappear in a test trial; network drops and
three unexplained restarts of the Pi interrupted sessions, and the trials they spoiled were voided or not counted and
were run again in later rounds (two voided and seven uncounted on sorting); a restart left a dead SSH connection file
that blocked the next session, which the client now detects and replaces. Because the Pi's download from the results
store over WiFi was slow, its sessions ran offline and were pushed at the end.

\section{WiFi against cable}\label{sec:edge-cable}
Each request carries the two camera images uncompressed, about 2.9~MB, so over WiFi the upload is a large part of
every round trip (Figure~\ref{fig:rttparts}). This matters more for \drtc{} than for the patient client. In a practice
round of E4 over WiFi, the first reply of \pizerofive{} took 2.2~s; \drtc's cooldown, set from the replies seen so far,
gave up the next requests as lost before their slow replies arrived, accepted one reply in total, and the run ended at
LeRobot's 10~s deadline for new actions. Diffusion Policy failed the same way, and one \smolvla{} trial with the stack
froze the control loop for 3~s and was stopped because its observation had become too old. E4 therefore runs with the
Pi connected to the laptop by an Ethernet cable, which shortens the upload; in the first E4 trial over the cable the
turnaround was 0.6--1.0~s. The difference between WiFi and cable is itself a result: a cooldown tuned on a fast link can
abandon every reply on a slow one (Section~\ref{sec:limits}).

\section{Summary}
This chapter showed that a Raspberry~Pi~5 can be the robot computer: it ran the official robot baselines of all seven
policies with the control loop at 29.9~Hz and no CPU limit. The link, not the Pi, is the constraint: over the WiFi
hotspot each request carried 2.9~MB of uncompressed images and the reply turnaround was 0.87~s at the median, three to
four times the bench's assumption, which made \drtc's cooldown abandon the replies of the slower policies. The robot
experiment E4 therefore runs over an Ethernet cable, and image compression is the next step for the edge.
